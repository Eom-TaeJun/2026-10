# 지원서에서 말할 주장과 증거

짧은 자기소개서 주장 설계와 3개 문장은 [application_claims.md](application_claims.md), 제출용 본문은 [portfolio.html](portfolio.html)에서 확인한다. 이 문서는 상세 증거·귀속·한계 기준을 유지한다.

## 전달할 핵심

현재 금융의 병목을 기술로 줄일 수 있는지 확인하고, 변화할 금융환경에서 필요한 데이터 구조를 미리 정의하는 역량을 보여준다. KB손해보험의 AI·데이터 직무에 대해 실제 내부 채용평가 기준을 안다고 주장하지 않는다. 공개 업무 소개와 장기보험 중심 손익 구조를 바탕으로, 실무자가 검토할 조건·근거·예외를 구분하는 작은 작업을 선택했다.

## 사용할 수 있는 표현

> 금융환경을 연구하면서 자산의 권리, 적용 조건, 효력 시점을 구분하는 것이 중요하다고 보았습니다. 이를 보험 업무의 데이터 검토 과제로 연결해, AI의 도움으로 합성 청구 증빙의 누락과 충돌을 담당자에게 넘기는 최소 실험을 구성했습니다. 사전에 고정한 평가 16건에서 규칙과 검토 이유가 일치하는지 확인했고, 정상 8건의 불필요 보류도 별도로 점검했습니다. 실제 약관 판단이나 지급 자동화 성과가 아니라, 업무 조건을 검증 가능한 데이터 기준으로 바꾸는 연습입니다.

> 권리가 세분화되는 미래에도 같은 시설의 장애 위험은 여러 계약에 함께 영향을 줄 수 있다고 생각했습니다. 가상 데이터센터 3곳과 권리계약 24건을 놓고 자산별 집계와 의존성·유효기간·권리종류를 연결한 집계를 비교했습니다. 네 사건에서 SQL 조인도 Python 규칙과 같은 결과를 냈습니다. 이를 통해 새로운 기술을 도입하는 것보다 필요한 관계와 예외를 먼저 정의하는 것이 중요하다는 점을 확인했습니다.

위 문장은 사용자 문제의식과 AI 보조 수행을 함께 밝힌 초안이다. 지원자가 코드를 직접 작성·설명할 수 있는 범위와 실제 참여 내역을 확인해 사용한다. AI 생성 코드 전체를 혼자 개발한 경험이나 실무 시스템 운영 경험으로 바꾸지 않는다.

## 주장 → 증거 → 한계

| 잠정 기여 | 남긴 증거 | 말하면 안 되는 확대 |
|---|---|---|
| 조건·시점을 데이터 검토 기준으로 바꾸기 | 합성 규칙 2개, 정상/예외 각 8건, 이유 및 인계 필드, 실행 로그 | 실제 KB 약관 버전 정확도, 보험금 지급 판단 |
| 정상도 해치지 않는 예외처리 평가 | A 정상 불필요보류 0/8. 이전 공개 검색 B 4/8 불필요보류도 별도 기록 | 모든 문의·실제 서류에서 오류가 사라짐 |
| 공동 의존성에 따른 집적 후보 찾기 | 계약 24개, 4개 사건, 알려진 한도와 미확정 항목 구별 | 실제 예상손실·자본요구량·보험료 산출 |
| 필요한 수준의 기술 선택 | 같은 입력의 의존성 SQL/Python 출력 4/4 일치 | 그래프·에이전트·블록체인 우월성 |
| 평가와 업무효과의 구분 | 정답 사전고정, 분모·원결과·제한 공개 | 직원 업무시간 절감, 운영 비용절감, 실제 고객효과 |

## 기여 주체와 면접 설명

- 사용자: 금융환경 변화, 권리·조건·시점 관점, 현재 병목과 미래 필요를 통해 직무 기여를 어필하려는 문제정의와 작업 방향 지정.
- AI: 공개자료 재확인·구조화, 합성 데이터/수작업 정답표 작성, Python/SQL 코드 구현, 시험 실행, 문서 초안 작성. 같은 AI 작성 주체이므로 독립 평가가 아니다.
- 아직 하지 않은 일: 사용자가 실제 고객/직원과 현장 검증, 운영 시스템 구축, 실제 실무 효과 측정, 독립 전문가 검토.

면접에서는 정상 건을 왜 보류하면 안 되는지, 만료 경계가 왜 필요한지, 한도 미상을 왜 0으로 바꾸면 안 되는지, SQL로 충분한데 블록체인이 필요한 조건은 무엇인지 설명할 수 있어야 한다. 다음 단계는 현장 담당자와 데이터·인계 기준을 합의하고 별도 평가자가 만든 새로운 표본으로 재검증하는 것이다. 현재 수치의 분모를 늘리는 반복 실행은 그 대안이 아니다.
